# LangRush Development Skill

## Tech Stack (do not deviate without discussion)
- Frontend: React (Next.js/Vite) + Tailwind CSS
- Game Engine: Phaser.js (HTML5 Canvas), embedded inside React
- Mobile: React Native + react-native-webview wrapping the same Phaser canvas
- Real-time sync & Auth: Firebase
- Backend API & DB: Spring Boot (Java) + PostgreSQL
- AI content pipeline: Python scripts + OpenAI/Claude API — pre-generates question batches directly into PostgreSQL, never called at runtime
- Deployment: Dockerized backend & DB on Ubuntu VPS + Nginx; frontend on Vercel; mobile app built via Expo

## Real-time data rules
- High-frequency state (player position, race progress, live sabotage events) MUST use Firebase **Realtime Database**, never Firestore.
- Low-frequency / structured state (room metadata, player list, lobby settings) may use Firestore.
- When a match ends, the room's "finished" state must trigger a sync of the final result into PostgreSQL via the Spring Boot API (prefer a Cloud Function trigger over polling). Firebase is never the permanent record of match history — PostgreSQL is the single source of truth for anything persistent.

## Security rules
- Never send the correct answer to the client before the player submits a response.
- All answers are validated server-side in Spring Boot, one question at a time — the client only ever sees the current question payload.
- Firebase Auth issues the identity token. Spring Boot must verify every request's token via the Firebase Admin SDK before trusting it — no endpoint trusts a client-supplied user ID directly.

## Conflict resolution
- Simultaneous sabotage actions targeting the same player resolve first-write-wins at the Firebase Realtime Database layer.
- Do not implement client-side conflict resolution for sabotage or race-position disputes — the server/DB write order is authoritative.

## Coding conventions
- Game logic (Phaser scenes, checkpoint/path logic, scoring) lives in one shared module reused by both the web build and the React Native WebView — never fork this logic per platform.
- Spring Boot follows Controller → Service → Repository layering strictly. No business logic inside controllers.
- Flashcard/question content is always pre-generated by the Python AI pipeline into PostgreSQL. Runtime application code never calls the OpenAI/Claude API directly.

## Review checklist for any change touching this project
1. Does this touch real-time state? Confirm Realtime Database is used, not Firestore, if update frequency is high.
2. Does this ever expose the correct answer to the client before submission?
3. If this touches match-end logic, does it sync the result into PostgreSQL?
4. Does mobile-specific code duplicate web game logic instead of sharing it?
5. Does any new Spring Boot endpoint verify the Firebase Auth token before trusting the request?
